# RK3568 四路 AI 摄像头项目技术总结

## 1. 项目当前状态

本项目目前已经实现了基于 RK3568 的四路摄像头实时采集、显示、AI 人体检测和可选 H.265 编码。系统运行在 ARM Linux 板端，摄像头输入为 4 路 `1920x1080@25fps NV12`，显示端使用 Wayland/EGL/GLES2，AI 使用 RKNN YOLOv5，编码使用 Rockchip MPP H.265。

当前代码分为两个主要版本：

- 稳定版本：`codex/stable-4ch-ai-enc-display`
- AVM/UI 开发版本：`codex/oem-avm-ui`

稳定版本主要保证四路采集、显示、AI、编码链路可用；AVM/UI 开发版本用于验证类原厂 360 环视界面、底部切换栏、AI 框叠加等交互效果。

## 2. 已完成能力

### 2.1 四路视频采集

系统通过 V4L2 MMAP 方式采集四路摄像头数据，每路摄像头输出 NV12 图像。采集线程负责从 `/dev/video0` 到 `/dev/video3` 拉取图像帧，并分发给显示、编码、AI 推理三条链路。

目前实现效果：

- 支持 4 路 `1920x1080@25fps` 输入
- 支持 NV12 图像格式
- 支持 DMA buffer fd 导出
- 支持四路独立采集线程

### 2.2 实时显示

显示采用 Wayland + EGL + GLES2。NV12 图像在 GPU 侧以 Y/UV 两张纹理上传，通过 shader 转换为 RGB 后显示。

当前显示模式包括：

- 2x2 四画面显示
- 单路/多路基础显示
- OEM AVM 实验界面
- 前视、后视、左视、右视切换
- 底部图标式切换栏

### 2.3 AI 人体检测

AI 推理使用 RKNN YOLOv5 模型，当前模型路径为：

```text
/userdata/yolov5.rknn
```

推理线程采用四路 round-robin 方式轮询摄像头，每次取一路图像进行预处理和 RKNN 推理。检测结果会过滤 person 类，并传回显示层。

目前能力：

- 支持四路轮询推理
- 支持 person-only 检测
- 支持检测框显示
- 支持检测日志输出
- 支持 AVM 大画面和单视角下叠加 AI 框

当前限制：

- 能识别“人在哪里”
- 不能直接输出真实距离
- 需要相机标定和地面映射后，才能把检测框转换为地面距离

### 2.4 H.265 编码

编码链路使用 Rockchip MPP 硬编码 H.265。编码开启后会将每路摄像头写入 `/tmp/cam_N.h264`。

目前能力：

- 支持 4 路 H.265 编码
- 支持 CBR 码率配置
- 支持编码和显示同时运行

当前现象：

- 不开编码时显示帧率较高
- 开编码后系统 DDR 带宽压力上升，整体帧率会下降
- 之前出现过编码开启后内存/生命周期问题，已经在稳定分支做过修复和隔离

## 3. 当前架构

整体数据流如下：

```text
V4L2 摄像头采集
    |
    |-- 显示链路：NV12 -> GLES 纹理 -> Wayland 显示
    |
    |-- 编码链路：NV12 -> MPP H.265 -> /tmp/cam_N.h264
    |
    |-- AI 链路：NV12/RGB 预处理 -> RKNN YOLOv5 -> 检测结果
```

线程模型：

```text
capture_thread x4
encode_thread  x4
infer_thread   x1
main/display   x1
```

主要模块：

```text
src/capture.c      V4L2 采集
src/pipeline.c     线程编排和 ring buffer
src/encoder.c      MPP H.265 编码
src/display.c      Wayland/EGL/GLES2 显示和 AVM UI
src/inference.cc   RKNN 推理
src/postprocess.cc YOLO 后处理
src/fisheye_mesh.c 鱼眼 mesh/后续矫正基础
src/main.c         程序入口
```

## 4. 当前 AVM 技术状态

当前 AVM 仍处于 UI 和交互验证阶段，还不是原厂级 360 环视。

当前已经做了：

- `/userdata/start_avm.sh` 启动脚本
- `/userdata/start_avm_enc.sh` 带编码启动脚本
- `OEM_AVM_MODE=1` AVM 模式
- 1/2 页全景辅助界面
- 3/4/5/6 页前后左右单视角
- 键盘数字键切换
- 鼠标点击底部工具栏切换
- AI 框叠加到大画面和单视角

但目前 1/2 页不是真正 BEV 鸟瞰拼接。没有完成相机标定之前，任何“假拼接”都会存在明显问题：

- 四路画面比例不准
- 拼接缝明显
- 物体位置不连续
- 鱼眼边缘畸变严重
- 无法准确表达车周围真实距离

因此，后续不建议继续靠 UI 强行假拼，应进入相机标定和地面投影路线。

## 5. 与原厂 AVM 的差距

原厂 AVM 通常包含以下技术：

```text
鱼眼相机内参标定
鱼眼去畸变
相机外参标定
地面逆透视投影 IPM
四路 BEV 拼接
重叠区域融合
车模遮罩
动态倒车轨迹线
雷达/距离告警融合
```

本项目当前已经具备：

- 四路视频输入
- GPU 显示
- AI 识别
- 编码保存
- 基础 AVM UI

暂未具备：

- 精确鱼眼去畸变
- 真实 BEV 鸟瞰投影
- 四路图像融合
- 人员距离估计
- 动态轨迹线
- 与雷达/车辆 CAN 数据融合

## 6. 为什么必须做鱼眼标定

当前摄像头是鱼眼镜头。鱼眼镜头的图像边缘存在强畸变，画面中的直线会变弯，物体尺寸和位置也会随画面区域变化。如果不做标定：

- 不能把图像点准确转换成真实地面点
- 不能计算人和车之间的距离
- 不能把四路画面拼成统一鸟瞰图
- 不能实现可靠的安全距离告警

鱼眼标定后可以得到每个摄像头的内参 `K` 和畸变参数 `D`。后续可以基于这些参数生成去畸变 mesh 或 LUT，在 GLES 中实时完成图像矫正。

## 7. 人员距离识别路线

当前 YOLO 检测只能输出：

```text
person 类别
置信度
检测框 x/y/w/h
```

它不能直接输出真实距离。

要实现人员距离，需要走以下路线：

```text
检测到 person 框
    |
取检测框底部中心点，近似为脚点
    |
鱼眼去畸变
    |
通过地面投影/IPM 转换到车体坐标系
    |
计算距离和方向
```

最终可以输出类似：

```text
cam2 person distance=1.8m zone=rear-left warning=yellow
cam0 person distance=0.7m zone=front warning=red
```

因此，人员距离识别和 AVM 标定是同一条技术路线。只要完成相机标定和地面映射，人员距离功能就可以继续实现。

## 8. 下一阶段建议

### 阶段 1：采集标定图片

使用板子上的实际摄像头拍摄棋盘格图片。建议棋盘：

```text
内角点：10 x 7
方格尺寸：40mm
实际格子：11 x 8
整体尺寸：440mm x 320mm
```

每个摄像头拍摄 30-50 张，覆盖中心、四角、边缘和不同倾斜角度。

### 阶段 2：离线鱼眼标定

在电脑上使用 OpenCV fisheye 模型进行标定：

```text
cv2.fisheye.calibrate()
```

输出每个摄像头的：

```text
K 内参矩阵
D 鱼眼畸变参数
去畸变 map 或 mesh
```

### 阶段 3：GLES 实时去畸变

在板子上不建议用 CPU 做 remap。建议使用 GLES mesh/LUT 方式，在显示阶段通过 GPU 采样完成去畸变，尽量减少帧率损失。

### 阶段 4：BEV/IPM 鸟瞰投影

在去畸变基础上，根据相机安装位置和地面平面关系，把四路画面投影到同一个车体坐标平面上，生成真正的鸟瞰视图。

### 阶段 5：距离告警和安防增强

基于 BEV 地面坐标，实现：

- 人员距离估计
- 前/后/左/右区域告警
- 近距离红色告警
- 中距离黄色提示
- 编码保存告警片段

## 9. 项目价值判断

当前项目已经完成了四路视频 + AI + 编码 + 显示的基础闭环，作为安防监控原型是合理的。它已经可以完成“多路画面查看、人员识别、编码保存”。

如果目标是接近原厂 AVM，还需要继续补齐标定、去畸变、IPM、融合和距离估计。当前最关键的技术瓶颈不是 UI，而是相机几何标定。

一句话总结：

```text
当前系统已经具备四路 AI 摄像头基础能力；
要从演示级 AVM 走向原厂级 AVM，下一步必须做鱼眼标定和地面投影。
```
